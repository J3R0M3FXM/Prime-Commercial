# Prime Commercial pre-cutover backup runbook

Status: tooling and procedure only. **No backup has been run by this document or by the migration branch.**

This is a required gate before any data import or production cutover. It covers two different artifacts:

1. An encrypted point-in-time **data and media snapshot** generated by the repository scripts.
2. A schema/function/trigger/policy dump from the Supabase CLI. The custom encrypted snapshot does not replace this SQL schema dump.

## 1. Protect the working environment

- Use a trusted local machine/Termux session and keep secrets in a local `.env` or secure environment manager only. Never paste service-role keys, database passwords, bot tokens, or the backup passphrase into chat or GitHub.
- Ensure `migration-backups/` is on encrypted device storage where possible. It is gitignored, and `.pcmbak` files are ignored.
- Pause writes/admin edits during capture if practical. The script paginates tables and storage objects; it is not a single cross-table PostgreSQL transaction.

## 2. Capture the encrypted data and storage snapshot

Install project dependencies first if they are not already installed. Export the following variables locally (do not commit them):

- `SUPABASE_URL` or `NEXT_PUBLIC_SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`
- `BACKUP_ENCRYPTION_PASSPHRASE` — strong, unique passphrase of at least 20 characters, stored separately from the backup file.

Then run:

```bash
node scripts/export-supabase-snapshot.mjs ./migration-backups/pre-cutover.pcmbak
node scripts/verify-supabase-snapshot.mjs ./migration-backups/pre-cutover.pcmbak
```

The exporter includes all 16 public application tables and recursively downloads objects from `product-images`, `receipt-proofs`, and `media-gallery`. The JSON payload is encrypted with AES-256-GCM and a per-file salt/IV. The verifier authenticates/decrypts it and rechecks row counts and SHA-256 checksums. It prints only counts and checksums, not record contents.

Keep the passphrase separate. A lost passphrase means the encrypted snapshot cannot be recovered.

## 3. Capture schema, functions, triggers, indexes, and policies

With the Supabase CLI authenticated and the project linked to the correct project ID:

```bash
mkdir -p migration-backups
npx supabase link --project-ref pcojgnqyjndplhhadzed
npx supabase db dump --linked -f migration-backups/schema.sql
npx supabase migration list
```

The CLI schema dump is a separate artifact; inspect its output and compare it with the checked-in migration history. Do not blindly run `supabase db push`, replay migration SQL, or apply any schema changes to the live project as part of backup capture. Store the dump securely and do not commit it.

Supabase CLI dump behavior and flags: https://supabase.com/docs/reference/cli/supabase-orgs

## 4. Repeat and reconcile

Before declaring the backup gate satisfied:

- Run the encrypted snapshot a second time after the write freeze.
- Compare per-table row counts and checksums between captures. Any difference requires investigation, not automatic acceptance.
- Compare the storage object paths, sizes, and checksums.
- Verify the schema dump contains the relevant public tables, functions, triggers, indexes, and policies. Supabase-managed storage metadata is not a substitute for the object bytes captured by the custom exporter.
- Record both encrypted artifact hashes, capture times, and who controls the recovery passphrase outside this repository.

## 5. Restore rehearsal — still required

A valid encrypted file is not yet a restore rehearsal. Before cutover, restore the snapshot into an isolated non-production target, preserving original IDs and JSON fields, and verify:

- all table row counts and checksums after round-trip;
- foreign-key-like references and orphan records (Telegram Serverless SQLite does not enforce foreign keys);
- monetary totals, order status/payment state, stock, bundle stock totals, loyalty/points balances, referral maturity state, promo redemption state, and payment audit events;
- every media object's byte checksum, content type, path, and access policy;
- receipt proofs remain private/access-controlled and payment secrets never appear in public endpoint responses;
- both unpaid-order expiry and referral-maturity behavior have a tested trigger strategy.

Do not cut over merely because the export and checksum verification pass. No production bot push, target schema migration, data import, or production cutover is authorized by these scripts.

## 6. Prepare Telegram media transfer (not executed)

The repository includes `scripts/migrate-media-to-telegram.mjs`. It decrypts the verified snapshot, checks each media object's checksum, verifies the configured Bot API token against `EXPECTED_TELEGRAM_BOT_ID` or `EXPECTED_TELEGRAM_BOT_USERNAME`, requires the configured storage chat to be a **private chat**, then uploads objects sequentially as documents. It writes an encrypted, resumable `*.pcmmapping` manifest with each object's original bucket/path, Telegram `file_id`, message ID, MIME type, size, and SHA-256. The script refuses to upload if the expected bot identity or private chat check fails.

Locally configure `TELEGRAM_BOT_TOKEN`, `TELEGRAM_STORAGE_CHAT_ID`, one expected bot identity variable, and `BACKUP_ENCRYPTION_PASSPHRASE`. Then run:

```bash
node scripts/migrate-media-to-telegram.mjs ./migration-backups/pre-cutover.pcmbak ./migration-backups/telegram-media-map.pcmmapping
```

This script has **not** been run. Do not run it until the exact Telegram Serverless bot is confirmed and the storage chat is controlled by the business owner. The encrypted mapping is only an inventory/transfer artifact; a target `media_assets` table, authenticated media-content endpoint, and frontend URL adapter still need to be implemented and tested. Receipt proofs must remain private and must never be bundled into the public static Mini App.

After the transfer manifest is created and independently checked, import its mappings into the target database with:

```bash
node scripts/import-telegram-media-map.mjs ./migration-backups/telegram-media-map.pcmmapping
```

This uses `npx tgcloud run endpoints/manageMediaAssets` in resumable batches; it does not deploy modules. Before running it, the target schema must have been reviewed and migrated, `system_settings.admin_telegram_user_id` must contain the authorized administrator ID, and the local CLI must be logged into the **same bot** verified in the encrypted manifest. The importer rechecks the Bot API token's bot ID and private storage chat before writing. If a batch fails, rerun the script; upserts are idempotent by bucket/path.
